## Protocol v2 features exercised

- Exact custom scope `custom:work_order:create`.
- `com.ratifyprotocol.allowed_values/v1` for the work-order category.
- `ratify.receiver_audience` with `expected_receiver_id` in every challenge.
- Integer `max_amount_micros`.
- 64-hex key IDs; root, status and agent keys pinned as complete keys.
- Signed status from the status publisher under a status key separate from
  the root key; the root key is refused as a status key.
- Challenges from the SDK issuance helper, bound to the action's session
  context, the expected agent key, and the receiver ID.
- A published signed receipt, the checkpoint acknowledgement, and release
  before every handler call, for allow and deny alike.

## Limits

- The claim store, receipt log, checkpoint, issuance store and security
  journal are the SDK's in-memory reference stores. They are not durable and
  the checkpoint runs in the receiver's process, so it is not an independent
  failure domain. This is a demonstration verifier, not a production-shaped
  one.
- The single-device offline profile (SPEC-v2 §7.13) does not apply to this
  connected hosted receiver and is not claimed.
- A signed status list is current for at most one day, so a v2 deployment
  needs a daily status signing step. Writing the list to the receiver's
  volume is not yet automated by `rotate_deployment_authority.py`.
- The packages are built from source, not installed from PyPI, so ISS-004 is
  open for v2 until `2.0.0b1` is published and pinned (`RATIFY_V2_PIN`).
- No v2 deployment, live gate, Maritime review, or published image exists.
  This reference is not described as v2-compatible on the strength of this
  record alone.
